# 策略目标 freshness 超时的 B1 修复记录

日期：2026-09-16。修复已完成编译和无硬件测试；真实机器人闭环复现及长时间运行尚未完成。

本次修复沿用现有线程、通道和动作处理结构，将结果准入年龄与已发布目标的保持时间分开，保留每轮正式推理的真实策略序号，并解耦准入计时和日志处理。40 ms 是已确认用于本轮测试的初始准入门限，不是已经验证安全的最终参数。

## 1. 故障现象与已有证据

运行日志显示，第 2695 次策略结果关联的命令触发 freshness 锁存，底层周期为 68347，原因编号为 1，即命令时效过期。策略命令 worker 同时报告目标年龄 60.669 ms，超过原 60 ms 截止期 0.669 ms；当时策略线程处于下一轮 inference 阶段，该阶段已持续 16.691 ms。随后 `policy_step()` 返回失败。

这些输出来自不同线程，终端文本可能交错。它们反映同一目标过期的保护链，不能仅凭交错日志推断成多个独立电机故障。

原逻辑将目标截止期设为最老电机或 IMU 主机观测时间加 60 ms。推理前观测已有的年龄、推理耗时以及之后的处理与传递，都消耗这段时间。worker 即使持续生成新电机命令，也只能保持原目标截止期。

已有 CSV `src/inference/log/0916_1618.csv` 显示：第 2695 轮推理开始时 IMU 观测已老化 18.428 ms，推理耗时约 25.497 ms；推理结束时最老观测年龄约为 43.926 ms。首条命令提交时，这个年龄已达到 44.675 ms，原目标寿命只剩约 15.325 ms。

CSV 没有记录精确的目标发布时间，因此不能把 44.675 ms 写成“观测到发布”的实测年龄。记录也没有第 2696 轮，不能证明丢弃 2695 后一定能及时恢复。

该次运行的推理平均耗时约 24.51 ms，已超过名义策略周期 20 ms，时间预算较紧。末轮 IMU 观测年龄明显增大，但缺少调度与传感器接收链路 trace，尚未唯一定位这次延迟的来源。原保护按原截止期语义触发；本次调整保护语义以容忍短暂延迟，不能据此认定原 watchdog 实现存在 bug。此前的[锁内存启动故障](2026-09-16_mlockall_ethercat_startup_failure.md)另有记录，现有证据未建立其与本次运行期超时的直接因果关系。

## 2. 修复一：结果准入与目标保持分别计时

推理和动作处理完成后，按最老电机、IMU 主机观测计算候选结果年龄。年龄大于 40 ms 时丢弃本轮结果；恰好 40 ms 允许发布。时间判断使用现有单调纳秒时钟，仅日志输出转换为微秒。年龄合格的重复观测时间戳允许发布，不新增时间戳必须前进的要求。

有效目标增加独立发布时间，截止期改为实际发布时间加现有 60 ms。worker 可以在期限内继续使用该目标，并结合最新电机反馈生成命令；重复生成命令不会续期。到达截止期即过期，保留原有锁存停机规则。

这两个门限不能解释为严格的 100 ms 观测到执行总年龄上限：40 ms 衡量准入时的结果年龄，60 ms 从实际发布起算，两者之间仍包含准入到发布的处理和调度间隔。

电机、IMU 主机时间戳缺失或出现负年龄时，继续沿失败路径停机。推理前已有的传感器年龄 50 ms、时间差 30 ms 保护保留。

底层命令截止期仍取“命令产生时间加 10 ms”和“目标截止期”中的较早者。首次正式推理开始时启动首帧 60 ms 计时，worker 独立检查；首个有效目标发布前的复位命令也受这个绝对期限封顶。电机命令接口新增默认不限制的可选绝对截止期参数，供首帧阶段传递该上限。

底层先检查已执行命令过期、再消费待处理新命令的顺序没有改变。因此，即使新目标已发布，若新命令传递过晚，仍可能因旧命令到期而锁存。

## 3. 修复二：策略序号保留丢弃轮次

`policy_seq` 从 1 开始，每轮正式推理分配一次，包括最终被丢弃的轮次。2026-09-17 简化后，目标和日志统一使用该序号，移除独立的 `target_seq` 计数器与字段。

例如，策略轮次 10 发布目标，轮次 11 被丢弃，轮次 12 再次发布目标。轮次 11 的日志保留真实 `policy_seq=11` 并标记丢弃；期间 hold 的目标来源序号仍为 10，下一目标来源序号为 12。

已发布目标和正常记录携带真实策略序号。底层 `source_policy_seq` 继续引用该序号，允许因 drop 跳号，仍拒绝序号回退；重复使用同一目标保持原来源。

drop 不发布、不更新时间、不提交候选 raw action，`policy_step()` 返回成功，让策略步、日志帧号与步态 phase 继续推进。已构建的观测历史保留；下一轮 `last_action` 沿用上一已发布目标的 raw action。重新初始化时重置策略序号和计时状态。

## 4. 独立修复项：准入计时与日志处理解耦

完成 inference 和 action processing 后，紧邻准入判断采样 `decision_now`。观测到结果年龄、上一有效目标的保持年龄都使用同一个决策时间，先决定 publish 或 drop，再组装固定大小日志记录。

保留目标帧内嵌 `InferenceRecord` 的结构。正常分支完成固定大小字段赋值及通道槽位复制后，在紧邻实际通道发布的位置另行采样 `published_at_ns`，设置截止期并立即发布。准入到发布之间不执行字符串构造、CSV 序列化、文件操作或 recorder 调用。

worker 仍负责补齐正常记录的首条命令信息。已完成日志的消费与 recorder 提交放在本轮 publish/drop 处理之后，CSV 序列化继续由原后台线程执行。

因此，判断后的日志处理延迟不会重算本轮两项年龄，也不会追溯改变准入结论。它仍可能影响后续轮次或已经发布目标的 hold 时间；60 ms 截止期始终使用实际发布时间。

## 5. CSV 与诊断语义

当前 CSV 在原列顺序末尾追加三列：`obs_to_action_age_us`、`target_hold_age_us`、`policy_result_dropped`。旧日志中的 `target_seq` 列保留为历史数据，新日志不再生成该列。

`obs_to_action_age_us` 表示本轮最老观测到准入决策的年龄。`target_hold_age_us` 表示同一决策时刻距离上一有效目标发布的时间；首帧前则从首次正式推理起点计算。正常行的 hold age 是本轮更新前的间隔，不是本轮新目标在首条命令提交时的年龄。

drop 行由策略线程直接提交 recorder：保留本轮真实 `policy_seq`，`command_applied=0`，`policy_result_dropped=1`；命令时间及截止期字段为 0，同时保留本轮输入和候选结果。正常行仍经过 worker 补齐命令信息。

沿用现有记录方式，正常行的 `command_applied=1` 表示命令提交接口已接受命令，不能单独证明底层实时线程或驱动已经执行。日志通道覆盖及 recorder 队列丢行行为也保留，CSV 不是连续 watchdog 采样。

超时错误文本输出故障当时实时计算的 `target_hold_age_us`，不将旧 `target_age_us` 改作新的含义。此前 CSV 两项年龄正常，不能单独证明之后的 watchdog 触发有 bug。

## 6. 验证结果

已完成 inference 全量编译，包含 `policy_test`；相关无硬件测试全量运行，17/17 通过，差异空白检查通过。自动验证未连接真实电机或获取 EtherCAT 硬件。

新增测试通过内部准入、发布与完成函数及测试友元，验证实际通道发布、状态推进和 recorder 记录，覆盖：

- 40 ms 准入边界、60 ms 到期边界、重复与缺失时间戳，以及原传感器年龄和时间差保护。
- drop 后策略序号前进、发布时间不刷新、候选 raw action 不提交，恢复后的目标保留策略序号跳号。
- 准入后模拟日志处理延迟，本轮年龄和结论不变，目标截止期从实际发布采样时间起算。
- 单次 drop 后恢复、连续 drop 到期、推理阻塞时 worker 独立保护、首帧期限、worker 停止刷新，以及截止期附近的新命令传递延迟。
- 底层接受来源策略序号跳号及同源 hold，拒绝回退，保留先检查旧命令过期的锁存顺序。
- 正常行与 drop 行的三个 CSV 新字段及策略序号、命令字段语义。

第 2694、2695 轮使用已有记录时间进行回放，目标发布时间采用推理结束至首条命令提交之间的边界，不猜测精确发布时间。第 2695 轮在推理结束时已经超过 40 ms，因此会归类为 stale result 并丢弃。单次 drop 后的恢复帧使用构造数据；它验证逻辑，不代表原运行实测恢复。

验证过程中还修正了既有配置测试对部署配置的错误假设：实际配置启用 raw action clip，测试却假定为 null。测试改为校验实际配置，并单独构造 null 配置验证关闭行为；没有为通过测试修改部署参数。

## 7. 后续板端验收

仍需在真实机器人上复现：孤立 stale result 被丢弃后，如果后续有效目标及命令在期限内送达，应恢复更新；连续无法产生有效目标应在 60 ms hold 到期后停机；worker 停止刷新应由独立命令期限保护。

还需长时间运行并结合实时超时文本、CSV 和调度或传感器接收记录，验证恢复与真实超时停机行为，确定 40 ms 初始门限是否适合最终部署，并继续定位观测延迟来源。现有记录不足以承诺本次完整运行一定避免停机。
